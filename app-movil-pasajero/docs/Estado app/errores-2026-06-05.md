# Registro de Errores y Soluciones - 05 de Junio de 2026

En este documento se registran los problemas de conexión y errores encontrados durante el desarrollo y las pruebas entre la aplicación móvil (React Native/Expo), el backend transaccional (Spring Boot) y el Motor de Inteligencia Artificial (Django).

## 1. Error de Login ("Credenciales incorrectas")
* **Síntoma**: Al intentar hacer login con el usuario `test@test.com` y la contraseña `123456`, el sistema arrojaba un error de "Credenciales incorrectas".
* **Causa**: La contraseña estaba guardada literalmente como el texto `123456` en la base de datos PostgreSQL. Sin embargo, el backend de Spring Boot (`AuthService` y `PasswordEncoder`) estaba diseñado para recibir la contraseña, calcular su hash en SHA-256 (codificado en Base64) y compararlo con el valor de la base de datos.
* **Solución**: Se generó el hash correcto (`jZae727K08KaOmKSgOaGzww/XVqGr/PKEgIMkjrcbJI=`) para la contraseña `123456` y se actualizó directamente en la base de datos mediante una consulta `UPDATE`.

## 2. Error de Red en el Login (`[TypeError: Network request failed]`)
* **Síntoma**: La petición del login desde la app móvil se quedaba cargando y luego mostraba el error de fallo en la red.
* **Causa**: El archivo de configuración de la app móvil (`config.ts`) estaba intentando conectarse a GraphQL apuntando al puerto `8080`, mientras que el servidor de Spring Boot estaba corriendo en el puerto `9090` según se indicaba en su archivo `application.properties`.
* **Solución**: Se modificó `GRAPHQL_URL` en `config.ts` para que apunte al puerto `9090` (`http://192.168.0.5:9090/graphql`), lo que permitió que la petición llegara al backend correctamente.

## 3. Error de Red al Analizar Imagen (`[TypeError: Network request failed]`)
El envío de la imagen de la cámara/galería al Motor IA de Django ha presentado una cadena de problemas de red. A continuación, lo que se ha hecho hasta ahora:

### Problema A: Host no permitido en Django
* **Causa**: El Motor IA estaba rechazando peticiones desde direcciones IP externas (como la `192.168.0.5` del celular en la red local) porque el archivo `settings.py` de Django tenía la configuración estricta por defecto (`ALLOWED_HOSTS = []`).
* **Solución**: Se cambió la configuración a `ALLOWED_HOSTS = ['*']` para permitir peticiones desde la red local durante el desarrollo.

### Problema B: Puerto bloqueado por el Firewall de Windows
* **Causa**: Tras arreglar el Host, la terminal de Django seguía sin recibir la petición, lo que indicó que el tráfico estaba bloqueado antes de llegar a Python. El Firewall de Windows suele bloquear el puerto `8000` si no se le concede permiso (a diferencia de Java que pide el permiso automáticamente la primera vez).
* **Solución**: Se deshabilitó Windows Defender temporalmente y se añadió una regla de Firewall para permitir explícitamente el puerto TCP 8000.

### Problema C: Cabecera HTTP incorrecta en React Native
* **Causa**: En el código de `BuscarImagenScreen.tsx` se estaba forzando la cabecera `'Content-Type': 'multipart/form-data'`. En React Native (y en los navegadores web en general), definir esto manualmente elimina el parámetro `boundary` (un separador necesario que el cliente de red genera automáticamente), lo que causa que el cliente de red (OkHttp) o el servidor aborten la conexión, devolviendo un error de red genérico.
* **Solución**: Se eliminó la asignación manual del `Content-Type` en el llamado a `fetch` para que React Native lo configure automáticamente con su `boundary` correcto.

## CAUSA RAÍZ REAL Y SOLUCIÓN DEFINITIVA (Resuelto)

> Nota: La hipótesis del "Cleartext HTTP de Android" quedó **descartada**. Si ese fuera el bloqueo, el login por GraphQL (también `http://` a la misma IP local, puerto 9090) tampoco funcionaría, y sí funciona. El problema era exclusivo del puerto 8000.

### Diagnóstico
1. El log de Django mostraba el servidor levantado correctamente en `http://0.0.0.0:8000/` pero **sin una sola línea de petición recibida** (`"POST /api/predict/"` nunca aparecía). Conclusión: la petición no llegaba al proceso de Python.
2. `Test-NetConnection 192.168.0.5 -Port 8000` desde la propia PC daba **timeout (~50s)** → firma típica de un paquete **descartado por firewall** (un puerto cerrado rechazaría al instante).
3. El Firewall de Windows estaba **activado** en los tres perfiles (Domain/Private/Public). La afirmación previa de "firewall desactivado" ya no era válida (se reactivó).
4. La red Wi-Fi activa (`FAMILIA RODRIGUEZ 2`) está clasificada como perfil **`Public`**.
5. Existían reglas de permiso para `python.exe`, pero apuntaban al **Python global** (`...\python311\python.exe`), mientras que Django se ejecuta desde el **entorno virtual** (`D:\Viajes-microservicios\env\Scripts\python.exe`), un ejecutable distinto sin regla que lo permitiera. Por eso Java (Spring Boot, 9090) sí funcionaba y Python (8000) no.

### Solución aplicada
* Se creó una regla de Firewall **por puerto** (no por programa, para que sea inmune a cambios de intérprete/venv):
  ```powershell
  New-NetFirewallRule -DisplayName "Motor IA Django 8000" -Direction Inbound -Protocol TCP -LocalPort 8000 -Action Allow -Profile Any
  ```
* Verificación: `Test-NetConnection 192.168.0.5 -Port 8000` → `TcpTestSucceeded : True`.

### Bugs adicionales corregidos en `BuscarImagenScreen.tsx`
* **Regex roto del nombre de archivo:** estaba `/\\.(\\w+)$/` (doble barra invertida) y nunca hacía match, dejando el `type` como `'image'` (sin `/`). El backend rechazaba con 400 al validar `content_type.startswith('image/')`. Corregido a `/\.(\w+)$/` con fallback `'image/jpeg'`.
* **Contrato de respuesta incorrecto:** el frontend validaba `json.exito` (campo inexistente). Django devuelve `{ reconocido, destino, confianza }` o `{ reconocido: false, mensaje, confianza_maxima }`. Se ajustó el parseo para usar `reconocido` y manejar el caso "sin coincidencias".
